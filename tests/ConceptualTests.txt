Use the practice data as described in ConceptualGraph.jpg for these tests
Perform these tests BEFORE integration with the RPI data. "Construction blocks"
refers to the data setting marking construction work on a pathway that makes said
path inaccessible. Look at map.jpg as the map for the data file.
1. Node A to Node A. Display an error message that the user isn't going anywhere.
2. Find a route from Node B to Node D (B -> D). Ensure this route is the same as the
   route from Node D to Node B (D -> B). Basic algorithm check.
3. Make a path from Node A to Node B. As a basic test of the contruction block modifier,
   this should result in the alternate route A -> C -> B being taken.
4. Starting from Node E, travel to Node H. This test is to ensure that when faced with
   multiple construction blocks around a destination node, all will be accounted for
   rather than just one.
5. Check to reach Node Y from any Node other than Z. This should return an error due to
   construction blocks preventing travel to Node Y. Make sure the error output properly
   conveys this to the user. This checks that construction is more than just a priority
   change.
6. Attempt to reach Node Z from any other Node. This is a check for an impossible
   route without any construction blocks as the cause. Display an error message
   conveying the failure to find an available route for the user.
Part 2: Advanced Conceptual Tests - Working with entrances and paths of different properties
Represented by AdvConceptualGraph.jpg
7. Attempt to find a path from Node J to Node L while avoiding stairs. It should display an error
   that the location cannot be reached without stairs. Simple test of the avoidance property.
8. Attempt to find a path from Node G to Node I while avoiding stairs. This valid path should
   acknowledge that the shorter paths aren't usable due to the stair restrictions across their
   paths, and go to from Nodes G to J to I.
9. Attempt to find a path from Node E to Node Y, with and without the avoid stairs toggle. This
   is a test that the addition of new features hasn't overridden the priority of avoiding closed
   paths.
Part 3: White Box Testing - Using the understanding of our current algorithm (If a location has
   multiple entrances, it will be referred to with a number added onto the Node letter)
10. Run a path from Node A to Node X. This should test whether the closest node to the
   destination node isn't prioritized when that closest node doesn't have a path to the
   destination.
11. Run two paths, one from Node F to Node G, and another from Node J to Node G. As they both
   will stop at different entrances of G(G1 & G2), this should be able to prove that all 
   entrances are accounted for as valid endpoints for a given location.
12. Run a path from Node D to Node K, no restrictions.This should go D -> E -> 1 -> F -> 
   G1 -> G2 -> K1. This should prove that pathfinding can use both entrance nodes and standard
   path nodes in the pathfinding.
13. Run a path from Node L to Node G1 while avoiding only steep slopes. This should take path
   L -> J -> K2 -> K1 -> G2 -> G1. This is a basic test of the toggle to avoid steep slopes.
14. Go from Node G1 to Node I1 while avoiding only stairs. This should go G1 -> G2 -> J -> I2 ->
    I1.
15. Go from Node L to Node K2 while avoiding only unpaved roads. This should go L -> J -> G2 ->
   K1 -> K2. This, alongside tests 13 & 14, work to ensure that paths can go through building
   entrances while also avoiding specific conditions.
